# 1. Overview

This document defines the database development standards for SyncBoard.

SyncBoard uses **Prisma ORM** with **PostgreSQL** to provide a type-safe, scalable, and maintainable database layer.

Prisma is responsible for:

- Database Access
- Schema Management
- Type Safety
- Migrations
- Transactions
- Query Optimization

Prisma acts as the bridge between the Repository Layer and PostgreSQL.

---

# 2. Objectives

After implementing this module, the backend should provide:

- Type-safe database queries

- Transaction support

- Scalable schema design

- Consistent database standards

# 3. Architecture

```
Next.js Frontend

↓

Express.js API

↓

Controller

↓

Service

↓

Repository

↓

Prisma Client

↓

PostgreSQL
```

Repositories are the only layer allowed to communicate with Prisma.

Services must never directly access the database.

Responsible for

- Models
- Relations

- Enums

---

### Prisma Client

Responsible for

- CRUD Operations
- Transactions

---

### Repository Layer

Responsible for

- Reading data
- Writing data
- Updating data
- Deleting data

Business logic must never exist inside repositories.

# 10. Audit Fields

Every major model should include

```
createdAt

updatedAt
```

Where applicable

```
createdBy

updatedBy
```

---

# 11. Soft Delete

Instead of deleting important records permanently

Use

```
deletedAt DateTime?
```

Advantages

- Recovery
- Audit History
- Safer Deletes

---

# 12. Transactions

Use Prisma Transactions for

- Board Creation
- Workspace Creation
- Invitations
- Bulk Updates

Never leave partial updates.

---

# 13. Query Optimization

Use

- select
- include
- pagination
- indexes

Avoid

```

with unnecessary include chains.
```

# 15. Indexing

Add indexes on

- updatedAt

# 16. Migrations

Every schema change must use

```
npx prisma migrate dev
```

Never modify production databases manually.

---

# 17. Seed Data

Provide seed scripts for

- Demo Workspace

---

# 18. Error Handling

Handle

- Unique Constraint Errors
- Foreign Key Errors
- Missing Records
- Transaction Failures

Return meaningful service-level errors.

---

# 19. Logging

Log

- Slow Queries
- Failed Queries
- Migration Errors

Never log sensitive information.

---

# 20. Monitoring

Track

- Query Duration
- Connection Count
- Transaction Time
- Slow Queries

Optimize frequently used queries.

---

# 21. Security

- Never expose Prisma directly to clients.
- Validate all input before database access.
- Prevent mass assignment.
- Use parameterized queries through Prisma.
- Restrict repository access.

---

# 22. Testing

Verify

- CRUD Operations
- Relations
- Transactions
- Migrations
- Soft Deletes
- Constraints

Automate database testing where possible.

---

# 23. Best Practices

- Keep Prisma inside repositories.
- Keep services database-independent.
- Never duplicate queries.
- Use transactions for critical operations.
- Avoid N+1 queries.
- Keep schema clean.
- Review indexes regularly.
